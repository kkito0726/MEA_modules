# `.hed` / `.bio` 読み込みのしくみ

MEA 計測データは `.hed` と `.bio` の **2ファイル1組**で保存されます。
このドキュメントは `read_MEA()` が**ビット列を電位データに変換するまでの処理を1手順ずつ**
解説したものです。

解析結果の数値（単位・測定範囲・時刻の起点）が何を意味しているのかは、この変換過程で
決まります。

| ファイル | 中身 | サイズ |
|---|---|---|
| `.hed` | **メタ情報**（サンプリングレート・GAIN） | 72 バイト固定 |
| `.bio` | **波形データ本体**（64電極分の生 AD 値） | 数十 MB〜 |

```python
from pyMEA import *

mea = read_MEA("/path/to/your_record_data.hed", start=0, end=30, electrode_distance=450)
```

利用者が指定するのは `.hed` のパスだけです。以降の Step 1〜6 が内部で実行されます。

> 📌 LPF / HPF（アナログフィルタ）の設定は `.hed` にも `.bio` にも**保存されていません**。
> 実験ノートに記録してください。検証の詳細は
> [`docs/investigation/hed_lpf_hpf_investigation.md`](../investigation/hed_lpf_hpf_investigation.md) を参照。

## 処理の全体像

```
  your_record_data.hed  (72 byte)
         │
         │  Step 1: int16×36 として解読
         ▼
    SAMPLING_RATE = 10000 Hz,  GAIN = 50000
         │
         │  Step 2: 拡張子を外して "0001.bio" を連結
         ▼
  your_record_data0001.bio
         │
         │  Step 3: start/end からバイト位置と要素数を計算
         │  Step 4: <h (リトルエンディアン int16) として読む
         ▼
    生AD値の1次元配列  [-32768 〜 +32767]
         │
         │  Step 5: × 200/32767      → μV へ換算 (GAIN=50000 基準)
         │  Step 6: × 50000/GAIN     → 実測GAINの測定範囲へ補正
         │  Step 7: (68, N) へ整形 → 先頭4語を破棄 → (64, N)
         │  Step 8: 時刻行を先頭に付与
         ▼
    (65, N) の配列
```

## 用語

| 用語 | 意味 |
|---|---|
| **AD値 / 生AD値** | AD変換器が出力した**整数**。`.bio` に保存されている値そのもの。単位を持たない |
| **AD変換 (Analog to Digital)** | 連続的に変化する電圧を、一定間隔で測って整数に置き換える処理 |
| **語 (word)** | ここでは int16（2 バイト）1 個分のこと。`.bio` は 68 語ごとに 1 フレームを構成する |
| **フレーム** | 1 時点分のデータ（68 語 = 136 バイト）。先頭 4 語 + 電極 64ch |
| **フルスケール / 測定範囲** | AD変換器が表現できる電圧の上限〜下限。GAIN で変わる（例: GAIN=50000 なら ±200 μV） |
| **分解能** | フルスケールを何段階に分けるか。16bit なので常に **65,536 段階** |
| **LSB (Least Significant Bit)** | AD値が **1 変わったときの電位の差**。「目盛り 1 個分」。`フルスケール全幅 ÷ 65534` |
| **GAIN** | 電極とAD変換器の間にあるアンプの増幅率。上げるほど測定範囲は狭く、1 LSB は細かくなる |
| **エンディアン** | 複数バイトの値をどちらのバイトから並べるかの規約。`.bio` はリトルエンディアン（下位が先） |

### AD値とは何か

電極が拾うのは**連続的に変化する電圧**（アナログ量）ですが、コンピュータは連続量をそのまま
保存できません。そこで AD変換器が一定間隔で電圧を測り、整数に置き換えます。

```
電極の電圧 (アナログ)         AD変換器          .bio に保存される値
  -4.4 μV, -3.1 μV, ...   →  16bitで数値化  →   -721, -508, ...
   なめらかな波形                                  整数の列
```

**AD値そのものには単位がありません。** 「何 μV か」の情報は AD値には含まれておらず、
**測定範囲（＝GAIN）と組み合わせて初めて電位に戻せます**。

定規に例えると、AD値は「**目盛りを何個分読んだか**」です。目盛りの総数は常に 65,536 個
（16bit なので固定）ですが、目盛り 1 個が何 μV かは測定範囲によって変わります。

そのため、**同じ AD値 `-721` でも GAIN が違えば意味する電位が変わります**。

```
GAIN=50000 (±200 μV)  →  -721 × 0.0061 μV  =     -4.4 μV
GAIN=5000  (±2 mV)    →  -721 × 0.0610 μV  =    -44.0 μV
GAIN=20    (±500 mV)  →  -721 × 15.2593 μV = -11001.9 μV
```

だからこそ、Step 1 で `.hed` から GAIN を読み取る必要があります。

> 💡 **飽和の判定は生AD値で見るのが確実です。** 値が ±32768 に張り付いていれば
> 測定範囲を超えており、元の波形は復元できません。

## Step 1: `.hed` を解読する

`.hed` は **72 バイト固定**のヘッダーファイルです。これを **int16 × 36 要素**として読み込み、
2つの要素をキーとして辞書を引きます。

```python
hed_data = np.fromfile(hed_path, dtype="<h")   # 72 byte ÷ 2 = 36 要素

rates = {0: 100000, 1: 50000, 2: 25000, 3: 20000, 4: 10000, 5: 5000}
gains = {16436: 20, 16473: 100, 16527: 1000, 16543: 2000,
         16563: 5000, 16579: 10000, 16595: 20000, 16616: 50000}

SAMPLING_RATE = rates[hed_data[16]]   # 要素16 がサンプリングレートのキー
GAIN          = gains[hed_data[3]]    # 要素3  が GAIN のキー
```

### `GAIN` のキーはなぜ 16616 のような半端な値なのか

**GAIN の実体は先頭 8 バイトに `float64` で直接格納されています。**
`gains` 辞書のキーは、その float64 の**上位 16 ビット**を int16 として読んだ値です。

GAIN = 50000 の実例（`.hed` 先頭 8 バイト）:

```
バイト列 (リトルエンディアン):  00 00 00 00 00 6A E8 40
                                                └──┬──┘
float64 として解釈  →  50000.0                    │
                                                   │
上位 2 バイト 0x40E8 を int16 として読む  →  16616 ← これが gains のキー
```

要素インデックスとバイト位置の対応は次のとおりです（int16 は 2 バイトなので `idx = byte / 2`）。

| 要素 | バイト位置 | 内容 |
|---|---|---|
| idx0〜3 | byte 0–7 | **GAIN の float64 実体**（idx3 = その上位ワード = 辞書キー） |
| idx8〜11 | byte 16–23 | サンプリングレートに反比例する float64（用途不明） |
| **idx16** | byte 32–33 | **サンプリングレートのキー**（`4 → 10000Hz`, `5 → 5000Hz`） |
| その他 | | 用途不明、または 0 |

サンプリングレートのほうは直接値ではなく**単なるキー**（`5 → 5000 Hz`）である点が
GAIN と異なります。

`.bio` のパスは、**`.hed` の拡張子を取り除いて `0001.bio` を連結**して作られます。

bio_path = os.path.splitext(hed_path)[0] + "0001.bio"

## Step 3: 読み出す位置とサイズを計算する

### `.bio` のフレーム構造

`.bio` にはヘッダーもフッターもありません。**「1 時点あたり int16 × 68 個」というフレームが
ひたすら並んだ**だけの構造です。

```
┌──────────── 1 フレーム = 68 語 = 136 バイト ────────────┐
│ w0 │ w1 │ w2 │ w3 │ ch1 │ ch2 │ ... │ ch64 │
└────┴────┴────┴────┴─────┴─────┴─────┴──────┘
  └── 先頭4語 (16語=8byte) ──┘  └─ 電極データ 64ch (128 byte) ─┘
       ↑ Step 7 で破棄
```

- 1 語 = int16 = **2 バイト**
- 1 フレーム = 68 語 = **136 バイト**
- 1 秒 = サンプリングレート × 136 バイト（10000 Hz なら 1.36 MB/秒）

### `offset` と `count` の計算

`np.fromfile` は**引数によって単位が違います**。

| 引数 | 単位 | 理由 |
|---|---|---|
| `offset` | **バイト** | ファイル内の位置（`seek` と同じ概念）。ヘッダは型サイズの倍数とは限らないため |
| `count` | **要素数** | 出力配列の長さを決めるため |

```python
bytesize = np.dtype("<h").itemsize   # = 2

offset = start * sampling_rate * bytesize * data_unit_length   # ← バイト
count  = (end - start) * sampling_rate * data_unit_length      # ← 要素数
```

どちらも出発点は「フレーム数 × 68」ですが、**`offset` だけ `bytesize`(=2) を掛けて
バイトに換算**しています。これは書き忘れではなく単位を合わせるためです。

`sampling_rate=10000`, `start=1`, `end=6` の場合:

| | 計算 | 結果 |
|---|---|---|
| スキップするフレーム数 | 1 秒 × 10000 | 10,000 フレーム |
| `offset` | 10000 × 68 × 2 | **1,360,000 バイト** |
| 読み込むフレーム数 | 5 秒 × 10000 | 50,000 フレーム |
| `count` | 50000 × 68 | **3,400,000 要素** |

この方式により、**ファイル全体をメモリに載せずに指定区間だけを直接読み出せます**。

## Step 4: ビット列を整数として解釈する

`dtype="<h"` は2つの部分に分解できます。

| 部分 | 意味 |
|---|---|
| `<` | **リトルエンディアン**（下位バイトが先） |
| `h` | **signed short = int16**（2 バイト符号付き整数） |

```
82 0F | 8A 4F | 00 00 | ...      ← ファイル上のバイト列
└─┬─┘   └─┬─┘   └─┬─┘
 3970   20362      0             ← <h として読んだ1要素
```

**2 バイトを 1 セットとして切り出し、それぞれが配列の 1 要素になります。**

### 16 ビットで表現できる値

```
1 バイト  = 8 ビット  = 2^8  =    256 通り
2 バイト  = 16 ビット = 2^16 = 65,536 通り   ← 256 × 256（足し算ではない）
```

符号付き（`h`）なので、この 65,536 通りを負にも配分します。

```
-32,768  ←────────  0  ────────→  +32,767
        │                       │
   0x8000                  0x7FFF
```

エンディアンを間違えても**エラーにならず違う数値が返ります**。同じ `82 0F` を各 dtype で
読んだ場合:

| dtype | 結果 |
|---|---|
| `<h`（正しい） | **3970** |
| `>h`（ビッグエンディアン） | -32241 |

だから `h` だけでなく `<` を明示的に書く必要があります。

## Step 5: 生 AD 値を電位に換算する

コード上の式はこうなっています。

```python
data = np.fromfile(...) * (volt_range / (2**16 - 2)) * 4     # volt_range = 100
```

### この式は「32767 で正規化する」ことと等価

一見すると `2**16 - 2` や `* 4` が何なのか分かりませんが、**代数的に整理すると単純な式になります**。

```
(volt_range / (2**16 - 2)) * 4
    │              │        │
    │              │        └─ 4 = 2 × 2
    │              └─ 2^16 - 2 = 65534 = 2 × 32767  (int16最大値の2倍)
    │
    ├─ 分母の「2倍」を 4 のうちの 2 が打ち消す
    └─ 残った 2 がフルスケールを ±2×volt_range にする

  ⇒  (2 × volt_range) / (2**15 - 1)  =  200 / 32767
```

この等価性は厳密です（浮動小数点でも一致します）。

```python
(100 / (2**16 - 2)) * 4  ==  (2 * 100) / (2**15 - 1)   # True
# どちらも 0.0061037018951994385
```

つまり式の意味は次の1行に尽きます。

```
電位 [μV] = 生AD値 / 32767 × 200
             └──┬──┘   └┬┘
        int16の最大値で   GAIN=50000 のときの
          正規化          フルスケール ±200 μV
```

`200` は **GAIN=50000 のときの測定範囲（±200 μV）** で、装置マニュアルの記載と一致します。

### 単位は μV（マイクロボルト）

`array[1]` 〜 `array[64]` の値の単位は **μV** です。mV ではありません。
pyMEA のグラフの縦軸ラベルが `Voltage (μV)` になっているのもこのためです。

### 実例（GAIN=50000 のデータ、frame 0 / ch 1）

```
生AD値 raw = -721

  -721 × (100 / 65534) × 4  = -4.400769
  -721 / 32767 × 200        = -4.400769   ← 同値

  → -4.400769 μV
```

## Step 6: GAIN で測定範囲を補正する

Step 5 の換算は **GAIN=50000 を基準**にしています。実測 GAIN が異なる場合は補正します。

```python
if gain != REFERENCE_GAIN:          # REFERENCE_GAIN = 50000
    amp = REFERENCE_GAIN / gain
    data *= amp
```

### なぜ「割る」ではなく「50000/GAIN を掛ける」のか

方向を間違えやすいので順を追います。

```
  同じ生体信号 V を測ったとき
     GAIN が大きい → アンプの出力が大きい → AD値も大きい
     GAIN が小さい → アンプの出力が小さい → AD値も小さい

  Step 5 の換算は GAIN=50000 のときに正しくなるよう較正されている

  ⇒ GAIN が 50000 より小さいと AD値が小さすぎるので、
     50000/GAIN 倍して元の大きさに戻す
```

GAIN=2000 なら `50000/2000 = 25` 倍します。

### 測定範囲の一覧

フルスケールは `±200 μV × (50000 / GAIN)` で決まります。
**8段階すべてが装置マニュアルの記載と一致することを確認済みです。**

| GAIN | 補正係数 | 測定範囲 | 1 LSB あたりの電位 | 主な用途 |
|---|---|---|---|---|
| 50000 | ×1 | **±200 μV** | 0.0061 μV (6.1 nV) | 微弱な信号 |
| 20000 | ×2.5 | ±500 μV | 0.0153 μV | 神経細胞のスパイク |
| 10000 | ×5 | ±1 mV | 0.0305 μV | |
| 5000 | ×10 | ±2 mV | 0.0610 μV | 心筋細胞の細胞外電位 |
| 2000 | ×25 | ±5 mV | 0.1526 μV | |
| 1000 | ×50 | ±10 mV | 0.3052 μV | |
| 100 | ×500 | ±100 mV | 3.0519 μV | |
| 20 | ×2500 | ±500 mV | 15.2593 μV | 大振幅・刺激応答 |

**GAIN を上げるほど測定範囲は狭くなり、分解能は細かくなります。**
分解能は常に 65,536 段階なので、測定範囲を狭めた分だけ 1 段階が細かくなる関係です。

```
1 LSB = 測定範囲の全幅 / 65534 = (2 × 200 × 50000/GAIN) / 65534
```

### GAIN の選び方

- **高い GAIN ほどノイズに強くなります。** アンプより後段（ケーブル・AD 変換基板・電源）で
  混入するノイズは絶対量が一定なので、入力に換算すると `1/GAIN` に縮みます。一方、電極や
  アンプ自身のノイズは信号と一緒に増幅されるため GAIN では改善しません。したがって
  **後段ノイズが十分小さくなったところで頭打ち**になります。
- ただし**測定範囲を超えると波形が頭打ち（飽和）になり、元に戻せません**。
- 目安は **信号のピーク振幅が測定範囲の 1/2〜2/3 に収まる範囲で、最も高い GAIN**。
  迷ったら 1 段下げるほうが安全です。

> ⚠️ 飽和の見分け方: `mea.data.array[1:].max()` が上表の測定範囲とほぼ一致していたら
> 飽和を疑ってください。生 AD 値が ±32768 に張り付いている状態です。

## Step 7: 配列を整形する

ここまでで得られるのは 1 次元の配列（長さ = フレーム数 × 68）です。これを 2 次元に直します。

```python
data = data.reshape(int(len(data) / 68), 68).T   # (N, 68) → 転置 → (68, N)
data = np.delete(data, range(4), 0)              # 先頭4行を削除 → (64, N)
```

```
1次元                (N, 68)                    (68, N)              (64, N)
[a0 a1 ... a67       ┌ a0 a1 ... a67 ┐          ┌ a0 b0 c0 ... ┐     ┌ ch1 の全時点 ┐
 b0 b1 ... b67   →   │ b0 b1 ... b67 │  転置 →  │ a1 b1 c1 ... │ →  │ ch2 の全時点 │
 c0 c1 ... c67       │ c0 c1 ... c67 │          │   :          │     │   :          │
 ...        ]        └   :           ┘          └ a67 b67 ...  ┘     └ ch64 の全時点┘
                       行 = 時点                  行 = チャネル       先頭4行を削除
```

**`np.delete` が転置の後にある**点が重要です。この順序により `range(4)` は「最初の 4 サンプル」
ではなく「**全フレーム共通の先頭 4 語**」を意味します。破棄される 4 語の中身は
[付録](#付録-破棄している先頭4語の正体)を参照してください。

## Step 8: 時刻軸を合成する

最後に時刻を先頭行として積みます。

```python
t = np.arange(len(data[0])) / sampling_rate   # 0, 1/rate, 2/rate, ...
t = t.reshape(1, len(t))
t = t + start                                  # 録画開始からの絶対時刻にする
data = np.append(t, data, axis=0)              # (64, N) → (65, N)
```

時刻は**装置が記録しているタイムスタンプではなく、公称サンプリングレートから合成**されます
（`k 番目のサンプル = k / サンプリングレート 秒`）。実測データ 28 ファイルで検証した限り
フレーム落ちは 1 件も無く、**サンプル間隔は装置のタイムスタンプと完全に一致します**
（起点だけ約 0.19〜0.20 秒ずれます。詳細は[付録](#付録-破棄している先頭4語の正体)）。

### `t + start` により絶対時刻になる

切り出した区間の相対時刻ではなく、**録画開始からの絶対時刻**が入ります。

```python
mea = read_MEA(hed_path, start=10, end=15, electrode_distance=450)
print(mea.data[0][0])     # 10.0   ← 0.0 ではない
print(mea.data[0][-1])    # 14.9999

mea = mea.init_time()     # 0 始まりに振り直したい場合
print(mea.data[0][0])     # 0.0
```

## 返ってくる配列と dtype

`mea.data` は **`(65, サンプル数)` の 2 次元配列**として振る舞います。

```
[0]   →  時刻データ (秒)
[1]   →  ch 1  の電位 (μV)
  :
[64]  →  ch 64 の電位 (μV)
```

**行番号がそのまま電極番号になる**（`mea.data[6]` が ch 6）ように、0 行目に時刻が入っています。

### dtype の使い分け（重要）

`read_bio` が返すのは `float64` ですが、`MEA` クラスが保持する際に**電位データは `float32` へ
変換されます**（元が 16bit なので情報の欠落はありません）。一方、時刻は `float32` だと
長時間記録で精度が足りなくなるため `float64` で別管理されています。

| 書き方 | 返るもの | dtype |
|---|---|---|
| `mea.data[0]` | 時刻軸 | **float64**（推奨） |
| `mea.data.times` | 時刻軸 | **float64**（同上） |
| `mea.data[6]` | ch 6 の電位 | float32 |
| `mea.data.array[0]` | 時刻軸 | float32（精度が落ちる） |
| `mea.data.array[6]` | ch 6 の電位 | float32 |

**時刻を扱うときは `mea.data[0]` または `mea.data.times` を使ってください。**

> ⚠️ `mea.data.time`（単数形）は**時刻軸ではなく記録長（`end - start` 秒）**です。
> 時刻軸は `times`（複数形）です。

## 実用上の注意点

### `end` が録画長を超えても例外になりません

`np.fromfile` は `count` がファイル残量を超えても**エラーを出さず、読める分だけ返します**。

```python
# 録画長が 4.6 秒のファイルに対して
mea = read_MEA(hed_path, 0, 10, 450)
print(mea.data.array.shape)   # (65, 23040) ← 10秒分ではなく 4.6秒分
print(mea.data[0][-1])        # 4.6078
```

「60 秒分のつもりで統計を取っていたら実は 5 秒だった」という取り違えを防ぐため、
**読み込み後に `mea.data.array.shape` か `mea.data[0][-1]` を確認する**習慣をつけると安全です。

その他のバリデーション:

- `start` / `end` が負の値 → `ValueError`
- `start > end` → `ValueError`

### メモリ使用量

保持されるデータは `float32`（1 要素 4 バイト）× 65 行なので、**`.bio` ファイルサイズの
約 1.9 倍**です（`260 バイト/フレーム ÷ 136 バイト/フレーム`）。

| サンプリングレート | 読み込み時間 | 保持されるメモリ |
|---|---|---|
| 10000 Hz | 1 秒 | 約 2.6 MB |
| 10000 Hz | 60 秒 | 約 156 MB |
| 10000 Hz | 300 秒 | 約 780 MB |
| 5000 Hz | 60 秒 | 約 78 MB |

計算式: `65 × サンプリングレート × 秒数 × 4 バイト`

**⚠️ 読み込み中のピークは保持量の約 4 倍。** Step 5〜8 の途中で `float64` の中間配列が
複数回作られるためです。10000 Hz / 60 秒の実測値:

| | 使用量 |
|---|---|
| 読み込み後に保持される量 (float32) | 156 MB |
| 読み込み中のピーク | **634 MB**（4.06 倍） |

対策の効き方は次のとおりです。

| 対策 | 効く場面 |
|---|---|
| `start` / `end` で必要な区間だけ読む | **読み込み中のピークにも効く**（唯一） |
| `down_sampling()` でサンプル数を減らす | 読み込み**後**のみ。ピークは下がらない |
| [`.npz` 形式](npz_io.md)で保存し直す | 次回以降の**再読み込み**のみ |

`read_MEA` の途中でメモリ不足になる場合は、`start` / `end` を分割するしか手がありません。
`down_sampling()` も `.npz` 保存も、一度フル解像度で配列を作った後の処理だからです。

## 付録: 破棄している先頭4語の正体

Step 7 で破棄される 4 語の中身は、実データ 28 ファイル・約 157 万フレームの解析により
判明しています。

| 語 | 内容 | 実測 |
|---|---|---|
| w0 | 固定マーカー | 常に **3970 (0x0F82)**、例外なし |
| w1 | 32bit カウンタの**下位 16bit** | uint16 として増加・ラップ |
| w2 | 32bit カウンタの**上位 16bit** | w1 のラップに同期して +1 |
| w3 | 常に **0** | 例外なし |

### w1 / w2 は 100 kHz のタイムスタンプ

2 つの 16bit 語をビット結合すると、1 つの 32bit カウンタになります。

```python
c32 = (w2 << 16) | np.uint16(w1)
```

```
        w2 (上位16bit)              w1 (下位16bit)
  ┌───────────────────────┐  ┌───────────────────────┐
  │ 0000 0000 0000 0111   │  │ 0100 1111 0011 0000   │
  └───────────────────────┘  └───────────────────────┘
    bit 31 ........... 16      bit 15 ........... 0

  w2 = 7, w1 = 20272  →  c32 = 7 × 65536 + 20272 = 479,024
                          → 479024 / 100000 = 4.79024 秒
```

この 32bit 値はフレームごとに**完全に一定の増分**で進みます（差分の不一致 **0件 / 28ファイル**）。
増分の値はサンプリングレートで決まります。

| sampling_rate | 増分/フレーム | 増分 × rate |
|---|---|---|
| 5000 Hz | 20 | 100,000 |
| 10000 Hz | 10 | 100,000 |

**増分 × サンプリングレート = 100,000 が常に成立**します。すなわち w1/w2 は
**100 kHz（分解能 10 μs）のマスタークロックを刻むタイムスタンプ**です。

`w1` を int16（符号付き）のまま読むと 32768 以上が負に折り返るため、結合するときは
`uint16` として解釈し直す必要があります。

### 計測トリガからの経過時間であり、日時ではない

全 28 ファイルの開始値が 0.187〜0.203 秒の狭い範囲に収まります。撮影日が異なる
（2023年 / 2026年）データでも同じ範囲なので、装置の連続稼働時間ではなく
**計測ごとにリセットされるカウンタ**です。**撮影日時は `.hed` / `.bio` のどこにも
含まれていません。**

### なぜ破棄してよいのか

- Step 8 の合成時間軸とは**定数オフセット（約 0.19〜0.20 秒）しか差がありません**。
  増分が完全に一定＝フレーム落ちゼロなので、サンプル間隔の点で両者は等価です。
- オフセットは装置トリガ基準の値で、ISI・FPD・伝導速度はいずれも時間差しか使わないため
  相殺されます。

唯一の活用余地は**フレーム欠落の検出**（増分が一定でなければ欠落確定）ですが、
28 ファイルで欠落は 0 件でした。
