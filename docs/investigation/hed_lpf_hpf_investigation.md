# `.hed` ファイルの LPF/HPF 情報調査メモ

調査日: 2026-06-20（2026-08-07 追記: フレーム先頭4語の解読結果を反映）

## 背景・目的

pyMEA の `read_MEA` は `.hed` ファイルからサンプリングレートと GAIN を読み込んでいる
（`pyMEA/infrastructure/read_bio.py` の `decode_hed`）。
この `.hed` には LPF / HPF の情報も含まれているはずという想定のもと、
`data/lpf_hpf/` のサンプルデータ（`<LPF>_<HPF>_.hed` 形式、計25種）を解析して
LPF/HPF を読み取るキーを特定し、読み込み機能を追加することを目的とした。

サンプル構成:
- LPF（ファイル名1要素目）: `2k / 3k / 5k / 10k / THRU`
- HPF（ファイル名2要素目）: `0.1 / 1 / 10 / 100 / THRU`
- 5 × 5 = 25 ペア（各 `.hed` + `0001.bio`）

## 結論（要約）

1. **LPF/HPF の設定は `.hed` にも `.bio` にも保存されていない。**
   - `.hed` 25個はバイト単位で完全に同一（md5 一致）。フィルタ設定が真逆のファイルでも中身が1ビットも違わない。
   - `.bio` はヘッダ/フッタを持たない純粋な信号データ。
2. **波形（`.bio`）からの推定可能性:**
   - **HPF: 精度良く判別可能**（低周波帯パワーが桁違いに分離）。
   - **LPF: 原理的にほぼ不可能**（サンプリング 5000Hz / ナイキスト 2500Hz に対し、カットオフ 3k/5k/10k/THRU が測定帯域外）。
3. `.hed` が持つ情報のうち pyMEA が利用しているのは **サンプリングレートと GAIN の2つだけ**。
   他にも非ゼロの値はあるが意味は不明で、いずれも LPF/HPF ではない。
4. （2026-08-07 追記）`.bio` フレーム先頭の予約4語は **固定マーカー + 100 kHz タイムスタンプ**
   と判明したが、フィルタ設定とは無関係だった。詳細4を参照。

## 詳細1: `.hed` にフィルタ情報は無い

### `.hed` 25個が完全一致

```
md5sum data/lpf_hpf/*.hed
→ 全25ファイルが同一ハッシュ: a9a873c8c608f2805e4cc72fcb9106d3
```

- 各ファイル 72 バイト（int16 × 36 要素）
- int16・生バイトどちらで比較しても、ファイル間で**変動する要素は1つも無い**

同一バイト列から異なる値は復元できないため、`.hed` 内に LPF/HPF を区別するキーは存在しない。

### `.bio` にもメタデータは無い

- `.bio` のファイルサイズは全て1フレーム（68 int16 = 136 byte）の整数倍ちょうど（余り0）→ ヘッダ/フッタ無し、純粋な信号データ。
- フレーム先頭の予約4語（`read_bio` で `np.delete(range(4))` される部分）は固定マーカーと 100 kHz タイムスタンプで、フィルタ設定とは無相関。
  詳細は下記「詳細4」および [`docs/api/hed_bio_io.md`](../api/hed_bio_io.md) を参照。

### 推定される理由

- 計測ソフトがフィルタ設定をヘッダに書き出していない、もしくは
- これらサンプルの `.hed` が単一テンプレートから複製されて作られた（md5 完全一致がこれを示唆）。

## 詳細2: 波形からの推定可能性

サンプリングレート = 5000 Hz（`.hed` デコード値）、ナイキスト周波数 = 2500 Hz。
全64ch平均の PSD（Welch法）を比較。

### HPF（ハイパス） → 精度良く判別可能 ✅

LPF=THRU 固定、2–10Hz 帯の平均パワー:

| HPF設定 | 2–10Hz帯パワー |
|---|---|
| 0.1 | 1.5×10⁵ |
| 1   | 1.1×10⁴ |
| 10  | 41 |
| 100 | 7.3 |

3〜4桁にわたり単調に分離。5択分類なら高精度で判別可能。

### LPF（ローパス） → 原理的にほぼ不可能 ❌

LPF カットオフ `2k/3k/5k/10k/THRU` のうち、**3k・5k・10k・THRU はすべてナイキスト 2500Hz より上**にあり、測定帯域内に現れないため区別不可能（標本化定理上の限界）。

HPF=1 固定、1800–2400Hz 帯の平均パワー:

| LPF設定 | 1800–2400Hz帯パワー |
|---|---|
| THRU | 2.85 |
| 10k  | 2.29 |
| 5k   | 2.09 |
| 3k   | 1.80 |
| 2k   | 1.41 |

差はわずかでノイズに埋もれるレベル。ナイキスト以下にある `2k` がかろうじて少し落ちる程度。

### 補足: `THRU_THRU` は飽和

フィルタを完全に外した `THRU_THRU` は ADC がレール張り付き（min -32768 / max +32767、std ≈ 19099）で信号として破綻。実用にならないエッジケース。

## 詳細3: `.hed`（72バイト = int16 × 36）の中身

非ゼロ領域（値は全25ファイル共通）:

| 位置 | 値 | 解釈 |
|---|---|---|
| **byte0–7 (float64)** | **10000.0** | **GAIN の実体** |
| byte16–23 (float64) | 2241023.8 | 不明 |
| byte4–7 (float32) | 6.110 | 不明 |
| byte20–23 (float32) | 12.069 | 不明 |
| **idx16 (int16)** | **5** | **サンプリングレートのキー → 5000Hz** |
| idx18,19 / idx22,23 (int16) | -1536,170 / -1537,170 | 不明 |
| idx30 (int16) | -1 (0xFFFF) | 不明（フラグ?） |

残りは全て 0。

### GAIN は本来 float64 で直接格納されている

現行コードは `gains = {16579: 10000, ...}` という辞書で **idx3 = 16579** から GAIN を逆引きしているが、
これは **byte0–7 の float64 値（= 10000.0）の上位16bit を読んでいるだけ**。

```
byte0-7 = 00 00 00 00 00 88 C3 40  →  float64 = 10000.0
idx3    = 0x40C3 = 16579           →  その上位ワード
```

GAIN の実体は byte0 の float64。サンプリングレートの方は idx16 が単なるキー（5→5000）で直接値ではない。

## 詳細4: `.bio` フレーム先頭4語の解読（2026-08-07 追記）

`data/lpf_hpf/` 25本 + `test/resources/` 3本、計 **28ファイル・約157万フレーム**を解析した結果、
`read_bio` が捨てている4語の正体が判明した。

| 語 | 内容 | 実測 |
|---|---|---|
| w0 | 固定マーカー | 常に **3970 (0x0F82)**、例外なし |
| w1 | 32bitカウンタの**下位16bit** | uint16 として増加・ラップ |
| w2 | 32bitカウンタの**上位16bit** | w1 のラップに同期して +1 |
| w3 | 常に **0** | 例外なし |

### w1/w2 は 100 kHz のタイムスタンプ

`c32 = (w2 << 16) | uint16(w1)` と結合すると、フレームごとの増分が完全に一定になる
（差分の不一致 **0件 / 28ファイル**）。増分の値はサンプリングレートで決まる:

| sampling_rate | 増分/フレーム | 増分 × rate |
|---|---|---|
| 5000 Hz（lpf_hpf 25本） | 20 | 100,000 |
| 10000 Hz（test/resources 3本） | 10 | 100,000 |

**増分 × サンプリングレート = 100,000 が常に成立**する。すなわち w1/w2 は
**100 kHz（分解能 10 μs）のマスタークロックを刻むタイムスタンプ**。
100 kHz は `decode_hed` の `rates` 辞書の最大値と一致しており、装置の基準クロックと考えて整合する。

### カウンタは計測ごとにリセットされる

全28ファイルの開始値が狭い範囲に収まっている:

| sampling_rate | c32[0] / 100000（秒） |
|---|---|
| 5000 Hz（25本） | 0.2010 〜 0.2034 |
| 10000 Hz（3本） | 0.1871 〜 0.1876 |

撮影日が異なる（2023年 / 2026年）データでも同じ範囲に入るため、装置の連続稼働時間ではなく
**計測トリガからの経過時間**である。日時情報はどこにも含まれない。
レートグループ内では狭く固まり、グループ間ではずれるが、理由は特定できていない。

### 捨ててよいと判断した理由

- `read_bio` の合成時間軸 `arange(N)/rate + start` とは**定数オフセット（約0.19〜0.20秒）しか差が無い**。
  増分が完全に一定＝フレーム落ちゼロなので、サンプル間隔の点で両者は等価。
- オフセットは装置トリガ基準の値で、pyMEA の ISI・FPD・伝導速度はいずれも時間差しか使わないため相殺される。
- 合成時間軸を実測タイムスタンプへ置き換えると `t` の起点が 0.19 秒ずれ、公開APIの契約が変わる。

唯一の活用余地は**フレーム欠落の検出**（増分が一定でなければ欠落確定）。ただし28ファイルで欠落は0件で、
欠落が起きうる装置かどうかの証拠が無いため、必要になった時点で検証ユーティリティとして追加すれば足りる。

### w3 について（未検証）

全ファイルで 0。48bitカウンタの最上位語である可能性はあるが、最長データが96秒なのに対し
w2 を符号なしと見ても w3 が非ゼロになるのは約11.9時間後で、手持ちのデータでは
「予約領域で常に0」と区別できない。

## 詳細5: 電位換算とGAINの検証（2026-08-07 追記）

装置マニュアルとの照合により、`read_bio` の換算式の意味が確定した。

### 換算式は「int16最大値で正規化してフルスケールに合わせる」だけ

```python
(volt_range / (2**16 - 2)) * 4  ==  (2 * volt_range) / (2**15 - 1)   # 厳密に一致
```

- `2**16 - 2` = 65534 = 2 × 32767（int16 最大値の2倍）
- `4` = 2 × 2。一方が上の「2倍」を打ち消し、もう一方がフルスケールを ±2×volt_range にする
- 実体は **`生AD値 / 32767 × 200 [μV]`**

### 単位は μV（コードのコメントが誤っていた）

`volt_range=100` でフルスケール ±200 μV。GAIN 補正 `REFERENCE_GAIN / gain` を掛けた測定範囲は
**8段階すべてが装置マニュアルの記載と一致**した:

| GAIN | 測定範囲 |
|---|---|
| 50000 | ±200 μV |
| 20000 | ±500 μV |
| 10000 | ±1 mV |
| 5000 | ±2 mV |
| 2000 | ±5 mV |
| 1000 | ±10 mV |
| 100 | ±100 mV |
| 20 | ±500 mV |

`read_bio` のコメントは `volt_range (mV)` となっていたが誤りで、正しくは μV。
プロットのラベル（`value_plots.py` の `Voltage (μV)`）や README_ja.md は元から μV 前提だったため、
**返り値の数値は元々正しく、コメントのみの不整合だった**。2026-08-07 に修正済み。

## 詳細6: `.hed` の追加検証（2026-08-07 追記）

`data/lpf_hpf/` 25本に `test/resources/` 3本を加えた28本で比較したところ、
**値が変動する要素は idx2, idx3, idx11, idx16 の4つのみ**だった。

- **idx2 / idx3** → 「詳細3」の byte0–7 float64（GAIN の実体）の下位・上位ワード。
  GAIN 3種で確認: `10000.0 → idx3=16579`, `2000.0 → idx3=16543`, `50000.0 → idx3=16616`。
  現行の `gains` 辞書が float64 の上位ワードを引いているという「詳細3」の説明を裏付ける。
- **idx16** → サンプリングレートのキー（`4 → 10000Hz`, `5 → 5000Hz`）。
- **idx11** → byte16–23 float64 の上位ワード。この float64 はサンプリングレートに反比例する:
  `5000Hz → 2241023.8`, `10000Hz → 1120511.9`（積はいずれも 1.1205119×10¹⁰ で一定）。
  録画長には依存しない。意味は不明。

**日時を示す要素は存在しない。** `.hed` からは撮影日時を復元できない。

## 今後 LPF/HPF 機能を実現する場合の選択肢

1. **未加工の `.hed` を別途入手して再検証** — フィルタ違いで中身が実際に異なる `.hed` が手に入れば、再度キー探索する価値あり（現サンプルは複製の疑いがある）。
2. **HPF のみ信号から推定する機能を実装** — 低周波帯エネルギー or ロールオフ勾配から推定。返り値はメタデータではなく「信号から推定した値」である旨を明示する必要あり。LPF はサンプリングレートを上げない限り推定不可。
3. **見送る** — 情報源が無いため、誠実には実装できない。

> 注意: 本サンプルは細胞データではなくフィルタ特性測定用の録音とみられる。
> 実際の細胞データでは信号の周波数成分が生物学的に決まるため、HPF 推定も「広帯域成分があること」が前提となる。
